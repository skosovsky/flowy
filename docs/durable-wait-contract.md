# Durable wait implementation contract

## Ownership and selected backend

Backoff discovery is opt-in under the same persisted runtime owner profile. Enabling DurableOptions.WaitProfile records that profile in the execution envelope; a differently configured runner must reject recovery before host callbacks. Plain executions without the profile retain caller-owned wakeup and are not silently adopted by discovery. InspectPendingActivityRetries exposes only sealed metadata (identity, current node/activation, exact token, immutable policy, attempt count and deadline). PostgreSQL DiscoverDueActivityRetries uses a transactional due projection indexed by persisted profile and deadline, with authoritative head revalidation and addressed corruption diagnostics; it never acquires a lease, calls Resume, classifies errors, resets deadlines or dispatches. The declared recovery owner routes the candidate to a compatible graph and calls Resume from its exact token. Runtime rechecks latest revision and the committed deadline/attempt limit under a live lease. Running/unknown/failed/completed activities, canceled/terminal executions and exhausted or not-yet-due retries are not runnable candidates. A candidate is an observation, not an acknowledgement or permission to retry ambiguous effects.

MVP backend is the optional PostgreSQL execution adapter. Core owns wait identity/FSM, compatibility, OCC/fencing and continuation publication; it does not import the database adapter. The same execution aggregate/history seals wait metadata and acceptance decisions. Memory conformance is useful but does not establish persistence after worker loss.

The backend capability profile explicitly identifies its journal/lease, timer delivery, clock and retry owners. A profile incompatible with the runner's execution store or a disabled capability rejects registration before an acknowledgement. Only one recovery owner coordinates an execution. Host deployment routing selects compatible executable graph/codecs; host authenticates transport and verifies business permission.

No distributed scheduler, cron language, operator UI or arbitrary mid-node signals are introduced. The selected adapter provides persisted due-wait discovery/delivery against its committed execution data; a host calls/drives that adapter rather than racing an independent scheduler for the same execution. IDs and clock are injected. Deadline scanning also needs an explicit policy for durable activity backoff so a prepared retry releases its worker and restart does not reset the deadline.

## Address and compatibility

A wait belongs to an execution/node/activation and stable wait ID. It carries correlation ID, absolute UTC deadline, matcher compatibility label, BYOT payload codec label, explicit winner policy and recorded event/timeout continuation contract. Runtime never infers absent labels or upgrades ordinary Suspend into a timer.

Registration validates targets/contract and persists the armed wait before any registration acknowledgement. If registration fails after arm commit, the armed record remains recoverable: no fake confirmed registration and no fabricated timeout. Re-registration uses the same identity and spec. A different spec for an existing logical wait is a typed conflict, not a new timer. Incompatible metadata rejects before payload/state decoding or host matcher/transition calls.

An armed durable wait is a safe boundary that releases the worker/lease. A parent cannot commit a later step or terminal while its current wait remains unresolved. A waiting recovery must not re-execute external node effects to poll for an event. State updates intended to precede the wait require an explicit saved boundary; the runtime must not silently discard mutated host state while preserving only the timer.

## FSM and arbitration

Delivery uses DeliverWait(executionID, delivery, contract). The host supplies labelled pure Match (for events) and Apply (for winner state transformation) functions; typed payload decoding remains host-owned. Labels must match the persisted matcher/payload/continuation contract before any callback or state decode. The method acquires an execution session with heartbeat, reloads its sealed latest aggregate, and does not execute graph nodes. Match receives detached bytes; Apply receives detached decoded state and a detached delivery. Winner state, selected event/timeout pointer, new activation and decision are committed together. Failed callback/encode/write/fencing publishes no acknowledgement or partial continuation. An identical duplicate and a losing delivery bypass matcher/state codecs/Apply; loser publication only adds its decision. Returned token resumes a winner separately; the method never implicitly calls Resume.

Persisted states are armed, resolved, expired and canceled. Records retain arm revision, resolution provenance and an identity-addressed decision ledger. A delivery identifies execution, wait/generation, correlation, event/delivery ID, kind and expected aggregate revision; its canonical payload digest prevents reuse of an ID with different data.

MVP winner policy is first valid committed resolution. A due timer may expire an armed wait; an accepted matching event may resolve it. The source revision and live fence are checked atomically with winner, accepted event ID and continuation. Concurrent event/timer callers cannot publish two continuations. OCC conflict is not evidence that an event was accepted.

After a competing resolution wins, the loser delivery is durably recorded against the same wait generation without rewriting the winner or applying its continuation again. A stale generation/future revision is rejected. A new unmatched event can record a rejection while keeping the wait armed. An already recorded identical delivery replays its previous decision/outcome, even after restart; a changed payload/kind under the same ID conflicts.

Matcher and state transition callbacks are pure host work. Runtime checks descriptor/codec labels before invoking them, maintains the acquired lease throughout them, rechecks cancellation/ownership before commit and discards their target on OCC/fence failure. No acknowledgement is issued before the durable decision is visible. Winner state/cursor and decision commit together, or an explicit recoverable acceptance protocol must prove that a crash cannot lose or duplicate continuation.

## Early/late delivery and cancellation

CancelWait(token, request) cancels only the addressed armed generation at its safe saved boundary. Request includes unique cancellation ID, reason and host evidence. Cancellation provenance and a failed terminal with reason durable_wait_canceled commit atomically, preserving state/effects; no codec, matcher, node or remote cancellation call is made. An identical cancellation replays without a write, while changed identity/evidence or stale revision rejects. Resolved/expired winners cannot be overwritten. Late deliveries store canceled rejection without clearing this terminal; Resume reports the persisted failure and cannot re-enter the waiting node. This terminal does not prove remote work stopped.

MVP early-event policy is explicit not-armed, with caller redelivery. There is no implicit unbounded inbox. Before arm commit, delivery returns typed not-armed and acknowledges no acceptance. Caller retains/retries according to its own transport policy.

Cancellation records canceled state at the same safe aggregate boundary. Late delivery may record a rejection but cannot restore armed state, clear terminal cancellation or execute a node. Timer cancellation and acknowledgement do not prove that an already dispatched remote activity stopped; existing unknown/fencing rules remain in force.

Typed failures distinguish unsupported capability/profile, unknown wait, not-armed, changed/duplicate identity, stale revision/generation, registration failure, unmatched event, expired/canceled wait and storage/ownership failure. A returned durable rejection decision must be distinguishable from a failure to persist that decision, so callers know whether redelivery is needed.

## Required implementation evidence

Use AAA and deterministic barriers/injected clock for event versus timer and duplicate delivery. Preserve every source record on failed matcher/transition/commit and verify zero incompatible decode/dispatch. Real-backend tests close/recreate pools between arm, delivery and continuation, and retain an old live connection for stale-owner checks.

Acceptance includes: armed restart with duplicate event/timer producing one continuation and persisted loser; absent/wrong adapter with zero registration promise; pre-arm not-armed; crash after acceptance with no lost/duplicated continuation; canceled run with late delivery and zero revival. Include stale ID/payload conflict, registration commit failure, lease loss during host callback, worker release, deadline retention and backend due-discovery recovery. Prune/retention must not erase decisions needed for delivery dedup under the declared retention policy.

## Implementation status

The arm API is a dedicated Await(spec) node directive, not a second implicit meaning of Suspend. The runner commits the reduced node state, effects, metadata and armed record together before calling the optional store's registration capability. A configured capability profile must match that same store and is persisted in the record; profile changes reject recovery before host decoding. A registration failure returns a recoverable token for the already armed boundary. Armed Resume retries the addressed registration without executing the waiting node; no new deadline/generation is fabricated. A disabled capability rejects the directive without an arm commit or registration acknowledgement.

The raw envelope now includes a sealed, detached wait payload. DurableWaitSpec requires explicit matcher/payload/continuation labels, correlation, UTC deadline and winner policy. Pure arbitration records event/timer acceptance, unmatched events, addressed loser decisions and immutable duplicate replay; it does not publish a continuation or acknowledge transport. Collection validation rejects inconsistent identities, generation, winner and provenance before domain decode. An armed wait blocks ordinary snapshot/step/terminal advancement.

PostgreSQL NewWaitExecutionStore opts the same execution store into a named owner profile. Registration verifies its committed armed generation; the aggregate itself is the durable registration, with no second index transaction. DiscoverDueWaits uses bounded keyset head scans (maximum 500), returns the current revision with each due candidate, and performs no lease acquisition or acceptance. Host drives complete scan cycles from the empty cursor under its declared clock; a candidate may become stale and must be revalidated by delivery. Ordinary NewExecutionStore has no enabled wait profile.

Atomic arm, registration fault recovery and node-free armed Resume are implemented and tested in memory conformance and PostgreSQL pool restart fixtures. DeliverWait now publishes winner decision/state/selected cursor/new activation in one fenced/OCC aggregate commit. Duplicate replay and durable loser/unmatched decisions bypass host state codecs and callbacks; new matching winners use labelled pure host callbacks with detached inputs and heartbeat. Callback/codec/commit failures return no accepted decision and preserve the source. A committed acceptance survives closing the original PostgreSQL pool before Resume; a new pool replays the event and records a competing loser without another callback, then executes the selected continuation once.

CancelWait now commits addressed cancellation provenance and its failed terminal together without codecs/nodes. Identical replay is read-only; changed evidence/identity, stale token and settled winner reject. Late delivery adds only canceled rejection, and Resume reports the persisted failure without re-entering the waiting node. Validation rejects canceled provenance without its exact terminal, activation/pointer, source chronology and evidence, even when the raw envelope is resealed. PostgreSQL tests close/recreate pools between cancellation, late delivery and Resume and verify no revival; cancellation write faults preserve the armed source.

The real stale-owner fixture retains a live old pool and uncanceled blocked matcher, expires its lease, publishes a timer winner from a separate pool, and then releases the old matcher. Its actual write is rejected specifically by ErrLeaseLost; the committed winner digest is unchanged and the old pool still responds to Ping. Both pools are then closed; caller redelivery through a fresh pool persists the unacknowledged event's loser decision and duplicate replay, without replacing the timer continuation. A separate fresh-pool concurrent event/duplicate/timer fixture proves one accepted decision, one durable loser and one selected continuation. Lease contention requires caller retry; it is not an acknowledgement. A real arm-commit barrier verifies ErrWaitNotArmed both before head creation and while an existing head's arm is uncommitted, with no head creation, mutation or callbacks. Caller rebinding to the committed generation and redelivery survive pool restart.

Opt-in activity-backoff discovery has a PostgreSQL pool-restart fixture: unbound and future heads produce no candidate, the due head preserves its policy/token/deadline, observation changes no history, and compatible Resume permits only the next bounded attempt. Profile mismatch rejects before callbacks; discovery selects only the configured persisted owner profile. Discovery is a read-only observation and does not create another scheduler/retry authority. Automatic durable prune/delete is rejected, preserving decisions and lineage rather than claiming an unimplemented dependency-safe retention policy. Host scheduling/transport authentication and compatible executable-code routing remain outside core. Current per-requirement evidence, final-audit status and delivery gates are recorded in task22-progress.md and the fixed requirement registry; stage tests alone do not establish full release readiness.
